# Story 2.2: Page Navigation

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to advance and return through story pages via swipe, tap zones, or VoiceOver actions,
so that I can read at my own pace regardless of input method.

## Acceptance Criteria

1. **Given** a reading page
   **When** the player swipes left or taps the right third of the reading card (UX-DR4)
   **Then** `advancePage()` is called and the next page renders

2. **Given** at least one page has been read
   **When** the player swipes right or taps the left third
   **Then** `goBack()` is called and the previous page renders

3. **Given** VoiceOver is active
   **When** the player uses the "Next Page"/"Previous Page" custom rotor actions
   **Then** the same advance/back behavior occurs (UX-DR12 — swipe is otherwise consumed by VoiceOver navigation, so this path must exist independently of the gesture)

4. **Given** a page contains an unresolved choice
   **When** the player attempts to advance (via any of the three input paths above)
   **Then** forward navigation is blocked (FR3). `StoryRunEngine.advancePage()` already no-ops on any non-`.reading` current node (Story 2.1's skeleton) — this AC is satisfied by every input path funneling through that same engine guard, never by the View independently deciding whether to allow the swipe/tap/rotor action (AD-3, AD-5)

5. **And** a Swift Testing case — extending the existing `ForkedEchoesTests/StoryRunEngineTests.swift` (do not create a second test file for engine logic) — verifies pager-gating explicitly for this story's scope: forward navigation is blocked while `currentNodeId` is an unresolved choice node, and forward navigation proceeds normally from the next reading node once `selectChoice(_:)` has resolved that choice (AD-7, NFR3)

6. **Given** this devcontainer has no Xcode/Simulator access, so swipe gestures, tap-zone hit-testing, and VoiceOver rotor actions cannot be exercised here (`project-context.md` Environment section)
   **When** implementation is complete
   **Then** the user separately confirms in Xcode/Simulator: swipe left/right and tap-zone taps advance/return pages identically, VoiceOver's "Next Page"/"Previous Page" custom actions behave the same as the gesture/tap paths, and forward navigation is genuinely blocked while sitting on Story 2.1's placeholder choice node (`.firstChoice`) — record what was checked and when in Completion Notes List (`project-context.md` Process Agreement — actively request this, don't just passively note it's unverified)

*(Flagged during Epic 1 retrospective, 2026-07-28: do not reuse `ColdLaunchOrientationFix`'s `.id(layoutGeneration)` mechanism as-is on this screen. It forces a full subtree teardown/rebuild on correction, discarding all nested `@State` — harmless on Home/Tutorial, destructive here once real pager position / in-flight choice-hold state exists. See the warning comment in `ColdLaunchOrientationFix.swift` and `project-context.md`'s Landscape/Orientation section. ### Architecture compliance (AD-3, AD-5, AD-7, AD-8)

- **AD-3**: Every interaction path that expresses the same intent — swipe, tap zone, VoiceOver custom action — must invoke the *same* `advancePage()`/`goBack()` method. These must never become separate code paths that could diverge (e.g. don't gate the swipe differently than the tap zone).
- **AD-5**: `StoryRunEngine`, not the View, decides whether a transition is allowed. The View's only job is translating each input (drag gesture, tap-zone tap, rotor action) into the matching intent call and letting `.transition`/`.animation` present whatever the engine's `currentNodeId` resolves to next. No `TabView(.page)`, no `NavigationStack` push/pop for individual pages — none of that changes in this story, just confirming the existing shape holds. Swipe/tap-zone recognizers are attached only to this reading surface (there is no interstitial view yet — Story 2.6 — so nothing to exclude them from today, but don't design them as globally attached either). **Superseded during this story's own implementation, 2026-07-31 — see Completion Notes for the full account:** the original plan (below) assumed `StoryChoiceView` would stay a `NavigationStack`-pushed destination, same as Story 2.1 shipped it. Real Simulator testing showed that push's system back button and `interactivePopGestureRecognizer` swipe gesture winning over this story's own swipe-right `DragGesture`, unconditionally, not just at the screen edge. AD-5 itself was amended (architect consultation, same day) so the Story session is presented via `.fullScreenCover` from Home/Tutorial instead of being pushed — see `ARCHITECTURE-SPINE.md`#AD-5 and `project-context.md`'s Navigation section for the corrected rule.
- **AD-7**: This story's Swift Testing scope is narrowly pager-gating (Task 1) — do not attempt to test choice-commit state machine (Story 2.3) or `RunSnapshot` (Story 2.4) here. No UI test target exists in this project (`project-context.md` Testing section) — the gesture/tap-zone/VoiceOver wiring itself is verified manually (Task 5), not by an automated UI test.
- **AD-8**: The tap-zone widths and swipe gesture are geometry/interaction concerns with an identical proportional split in both orientations — no `verticalSizeClass` branch needed for anything in this story.

- **Second real bug found and fixed via user testing (2026-07-31): `NavigationStack`'s interactive pop gesture was winning over this story's own swipe-right `DragGesture`.** User reproduced it from `.intro` (the very first page — `goBack()` there should be a pure no-op, empty history): swiping right, from *either* the left edge or the middle of the screen, popped the entire `StoryChoiceView` off the nav stack back to Home, instead of the engine's `goBack()` no-op.
