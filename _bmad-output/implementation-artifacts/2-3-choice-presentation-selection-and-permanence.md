# Story 2.3: Choice Presentation, Selection & Permanence

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to make a permanent choice via press-and-hold or a quick tap,
so my decision sticks and the story moves forward.

**RESOLVED CONFLICT (2026-08-01, user + architect call during dev-story):** epics.md's original AC #3/#7 wording ("commits instantly," "unblocks navigation immediately, independent of the undo window") contradicted both AD-3's own prose ("`selectChoice(_:)` fires exactly once, at the moment the interaction finalizes — charge completes, **or the undo window elapses without a cancel**") and the actual intended UX: a genuine reconsideration window before a choice is irrevocable. Corrected model, confirmed with the user:
- **Hold:** `selectChoice(_:)` fires only when the 3s charge completes. Releasing early is a full cancel — the engine is never touched.
- **Tap:** the card visually locks (checkmark) *immediately* on tap — no charge animation to wait for — but the actual `selectChoice(_:)` call is deferred until the 1.5s undo window elapses. A second tap on the same card within that window fully cancels (engine untouched, since `selectChoice(_:)` hadn't fired yet — nothing to "undo" at the engine layer). Letting the window elapse without a second tap is what finalizes the commit.
- **Either path:** forward navigation stays blocked the entire time the choice isn't yet finalized, because `currentNodeId` genuinely hasn't moved — this is `advancePage()`'s existing no-op-on-non-`.reading`-node guard (Story 2.2), completely unchanged. No new engine code anywhere in this story.
- Revisiting a decided page later via `goBack()` shows it locked/highlighted, driven purely by `engine.choiceHistory` — matches AC #5 and the user's own description of swiping back to the choice page after reaching its target.
- AC #3 and AC #7 below are corrected to match. `epics.md` itself is out of scope to edit from this story file, but this resolution is the authoritative one for implementation — flag the epics.md wording drift for a future docs pass, same as `ARCHITECTURE-SPINE.md`#AD-5's amendment was flagged after Story 2.2.

## Acceptance Criteria

1. **Given** a choice page with ≥2 options
   **When** rendered
   **Then** each is an independently selectable Choice card (UX-DR3); only one card can charge at a time (holding a second cancels the first)

2. **Given** a press-and-hold on a choice card
   **When** the hold reaches ~3s (`LayoutMetrics.choiceChargeDuration`)
   **Then** the choice commits via `engine.selectChoice(_:)`; releasing early cancels to idle with no partial memory — the engine is never called

3. **(Corrected, see RESOLVED CONFLICT above) Given** a quick tap (or VoiceOver double-tap)
   **When** activated
   **Then** the card visually locks to selected styling with a checkmark *immediately*, but `engine.selectChoice(_:)` itself does not fire yet — a 1.5s undo window (`LayoutMetrics.choiceUndoWindow`) opens, during which tapping the same card again fully cancels (reverts the visual, engine untouched, exactly as forgiving as releasing early on the hold path); letting the window elapse without a second tap is what actually calls `engine.selectChoice(_:)`

4. **Given** a choice finalizes (hold-complete, or tap-undo-window-elapsed)
   **When** `selectChoice(_:)` fires
   **Then** forward navigation unblocks (already true — `StoryRunEngine.advancePage()`'s existing no-op-on-non-`.reading`-node guard, Story 2.2, since `currentNodeId` has now genuinely moved), the card is already showing its locked/checkmark styling (was shown instantly on tap, or built up via the charge fill on hold), and the choice's alignment delta accumulates into `alignmentScore` (FR7's accumulation mechanism — engine-only, never exposed in any Epic 2 UI)

5. **Given** a decided choice page revisited via back-navigation
   **When** rendered
   **Then** it shows the made choice locked, with no alternate-choice control at all (FR5) — no other card is tappable/hold-able once one option has a `choiceHistory` entry for that node

6. **Given** the app terminates mid-charge or mid-undo-window
   **When** relaunched
   **Then** the choice page shows undecided — nothing was committed (AD-3: charge/undo state, and the deferred `selectChoice(_:)` call itself, are View-local `@State`/`Task` until finalization; termination before that point means the engine was never touched)

7. **(Corrected, see RESOLVED CONFLICT above) Given** a quick tap has visually locked a card and its 1.5s undo window is still open
   **When** the player attempts to page forward before the window elapses
   **Then** forward navigation is still blocked — `selectChoice(_:)` hasn't fired yet, so `currentNodeId` hasn't moved, so `advancePage()`'s existing guard still applies; only once the window elapses (finalizing the commit) does forward navigation unblock

8. **Given** `DESIGN.md`'s specified timings (3000ms charge, 1500ms undo window) are unvalidated placeholder-quality values
   **When** implemented and tried by hand on a real device
   **Then** these durations may be tuned by feel — they are a reasonable starting point, not a locked spec; if adjusted, update `DESIGN.md`'s token values (`components.choice-card.charge-duration` / `.tap-undo-window`) to match what actually shipped

9. **And** a Swift Testing case — extending `ForkedEchoesTests/StoryRunEngineTests.swift` — verifies the choice-commit state machine at the engine boundary: `selectChoice(_:)` accumulates `alignmentDelta` into `alignmentScore` and appends the correct `ChoiceRecord` on commit, is a no-op if called again on an already-decided node (permanence — this guard already exists from Story 2.1, but this story's own commit paths route through it for the first time in real UI, so add a test that pins it explicitly for this story's traceability), and never fires unless `selectChoice(_:)` itself is called (i.e. no engine mutation happens just from charging or from the undo window being open — since charge/hold/undo state is entirely View-local `@State` per AD-3, this is really an assertion that the View-layer interaction described in AC #2/#3/#6 has nothing to test at the engine layer beyond "the engine only ever changes on an actual `selectChoice(_:)` call," which is already implicit in every existing engine test — state this explicitly as a Dev Note rather than inventing an artificial engine-level test for View-local behavior that has no automated coverage path, per `project-context.md`'s Testing section: no UI test target exists)

10. **Given** this devcontainer has no Xcode/Simulator access, so press-and-hold charge timing, tap-then-undo-window behavior, and VoiceOver double-tap commit cannot be exercised here (`project-context.md` Environment section)
    **When** implementation is complete
    **Then** the user separately confirms in Xcode/Simulator: holding a card to ~3s commits it with checkmark styling and unblocks forward navigation; releasing early cancels with no visual/engine trace; holding a second card while one is charging cancels the first; a quick tap commits instantly, opens the 1.5s undo window, and a second tap within that window reverts the visual selection (engine state is unaffected either way, since `selectChoice(_:)` already fired — AC #7); revisiting a decided choice page via back-navigation shows the locked choice with no other card interactive; VoiceOver double-tap on a card behaves like a quick tap. Record what was checked and when in Completion Notes List (`project-context.md` Process Agreement — actively request this, don't just passively note it's unverified)

### Architecture compliance (AD-3, AD-4, AD-5, AD-7, AD-8)

- **AD-3** (`ARCHITECTURE-SPINE.md`#AD-3, explicitly calls out this exact interaction): "A choice's press-and-hold charge and its tap-then-1.5s-undo-window ... are entirely View-local, transient, uncommitted state (`@State`) — `selectChoice(_:)` fires exactly once, at the moment the interaction finalizes ... never eagerly and never revocably. If the app terminates before finalization, nothing reached the engine — relaunch shows the same choice page, undecided." This is the architectural spec for AC #2/#3/#6 — implement charge/undo entirely as `@State` in the View layer, never touching the engine until the exact commit moment.
- **AD-4**: `RunSnapshot`/persistence is Story 2.4's job — this story's `alignmentScore` accumulation happens in-memory only (already true of `StoryRunEngine` since 2.1); nothing here should attempt to persist anything.
- **AD-5**: The View translates input (hold-complete, tap-then-elapsed-undo-window) into the single `selectChoice(_:)` intent; the engine's own guards (permanence, node-type) remain the sole source of truth for whether anything happens. Same pattern as Story 2.2's swipe/tap-zone/rotor → `advancePage()`/`goBack()`.
- **AD-7**: Testing surface is narrow — `selectChoice(_:)`'s accumulation/permanence behavior (Task 1). The charge/hold/undo *View* interaction has no automated coverage (no UI test target exists) — verified manually only (Task 6). Don't invent a UI test.
- **AD-8**: `DESIGN.md components.choice-card.layout-landscape` specifies choice cards switch from vertical stack to horizontal row in landscape once the reading surface is styled (Story 2.8's job) — this story's minimum-viable card layout does not need to implement the landscape row variant; a plain `VStack` of cards (matching the current `.choice` case's `VStack` shape) is acceptable for this story, deferring the `verticalSizeClass`-branched row layout to 2.8 alongside the rest of the visual identity pass. Don't build the landscape row layout prematurely without the surrounding visual polish it depends on.

- **`ChoiceCardView.swift` (new file), first pass:** both press-and-hold and quick-tap were originally planned as two separate gesture recognizers — a `.highPriorityGesture(DragGesture(minimumDistance: 0))` for the charge, plus a co-attached `.onTapGesture` for the tap. **User Simulator testing found this broken: a quick tap did nothing.** Root cause and fix documented in the "Round 2" note below.
- **Round 2, user Simulator testing (2026-08-01): two real bugs found and fixed.**
  1. **Quick tap did nothing.** A zero-distance `DragGesture` attached via `.highPriorityGesture` matches *every* touch, including an instantaneous tap — so it always won and consumed the touch before the separately-attached `.onTapGesture` ever saw it, silently discarding every tap as a "charge that got released immediately." **Fix:** consolidated both interactions into the single `DragGesture` — `touchDown()`/`touchUp()` measure the actual contact duration and classify it against the new `LayoutMetrics.choiceTapMaxHoldDuration` (300ms, no DESIGN.md token, tunable by feel): under the threshold locks the card and starts the undo-window `Task`; over the threshold (but under the full charge duration) is a cancel. Also added an explicit `.accessibilityAction` (`handleAccessibilityActivate`) for VoiceOver, since double-tap-to-activate bypasses the raw `DragGesture` pipeline entirely and the earlier "`.onTapGesture` gets VoiceOver for free" assumption no longer applies once `.onTapGesture` itself was removed.
  2. **Revisiting a decided choice page via back-navigation, then trying to page forward again, went nowhere.** Traced to a **pre-existing Story 2.2 defect**, not a regression from this story: `StoryRunEngine.advancePage()` unconditionally no-op'd on *any* non-`.reading` node, including an already-decided `.choice` node — a Story 2.2 test (`advancePageRemainsBlockedOnAChoiceNodeEvenAfterItHasBeenResolved`) explicitly asserted this permanent block, but that contradicted `ARCHITECTURE-SPINE.md`#AD-5's own documented wording ("blocks forward on an **unresolved** choice"). It never surfaced until this story's real choice-selection UI made "go back to a decided page, then page forward again" an actual thing a player does. **Fix:** `advancePage()` now follows a decided choice node's recorded `choiceHistory` target, exactly like a reading node's `next` link — still no-ops on an unresolved choice node. The outdated test was rewritten (`advancePageProceedsFromADecidedChoiceNodeToItsRecordedTarget`) to assert the corrected behavior; `swift test` 15/15 passing throughout.
- **Only-one-card-active enforcement (AC #1):** `StoryChoiceView` owns a shared `@State private var activeChoiceOptionID: ChoiceOptionID?`, passed to every `ChoiceCardView` as a `Binding`. A card claims it on touch-down/first-tap and each card observes `.onChange(of: activeOptionID)` to reset itself back to idle if another card claims it — correctly cancels an in-progress charge or undo window if a second card starts an interaction.
- **Decided-page rendering (AC #5, AC #6):** `StoryChoiceView`'s `.choice` case derives `decidedRecord` from `engine.choiceHistory.first(where: { $0.nodeId == engine.currentNodeId })` on every render — the sole source of truth, since neither `StoryChoiceView` nor `ChoiceCardView` persists any "was mid-interaction" state (correctly, since a real termination mid-charge/mid-undo-window loses that `@State` entirely, satisfying AC #6 — today this is also true trivially, since `RunSnapshot` persistence doesn't exist yet until Story 2.4, so *any* app termination currently loses all engine state regardless of this story's design). Because `onFinalize` never fires until true finalization, `engine.choiceHistory` never contains an entry for the current node while a charge/undo window is in flight — no special-casing was needed for "decided but still reconsiderable," simplifying Task 3 from what was originally planned.
