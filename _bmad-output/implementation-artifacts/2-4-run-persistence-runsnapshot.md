# Story 2.4: Run Persistence (RunSnapshot)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want my in-progress run saved automatically,
so that a relaunch or backgrounding doesn't lose my place.

## Acceptance Criteria

1. **Given** any completed mutating intent (`selectChoice(_:)`, `advancePage()`, `goBack()`)
   **When** it completes
   **Then** `RunSnapshot` (`currentNodeId`, `choiceHistory` as ID pairs, `alignmentScore`, `tutorialSeen`) is encoded and written synchronously (never debounced/async) to its single `UserDefaults` key, `RunSnapshotPresence.runSnapshotKey` (AD-4)

2. **Given** a cold launch with a valid snapshot
   **When** the app starts
   **Then** the engine decodes it and resumes at the saved node with full `choiceHistory` and `alignmentScore` restored

3. **Given** a decode failure of any kind (missing key, malformed JSON, or a `currentNodeId`/choice option id that no longer resolves against the current `Content` tree)
   **When** encountered
   **Then** the engine falls back to a fresh run at `StoryTree.root` exactly as if no snapshot existed — no crash (NFR4)

4. **Given** Home's Story 1.2 presence-only check (`RunSnapshotPresence.hasInProgressRun`)
   **When** this story's decode-failure handling lands
   **Then** Home's Resume/Start label is driven by decode *success*, not mere key presence — a corrupted snapshot falls back to fresh Home and shows "Start Story," never "Resume Story" followed by a silent fresh-start

5. **Given** the current node becomes an `.ending` node (reached via `selectChoice(_:)`'s hard-fail bypass or ordinary `advancePage()`/`selectChoice(_:)` traversal into a terminal node)
   **When** that transition completes
   **Then** the `RunSnapshot` is cleared (`UserDefaults` key removed) rather than written — a finished run has nothing to resume, and Home must never keep showing "Resume Story" pointing at a completed run (AD-4: "reaching the Ending phase clears it"; this closes the exact drift the architecture's adversarial review flagged as a real bug class, see Dev Notes)

6. **And** a Swift Testing case verifies `RunSnapshot` encode/decode round-trip (including `alignmentScore` and `choiceHistory`), the decode-failure fallback (missing key, malformed data, and an unresolvable `currentNodeId`), and that reaching an `.ending` node clears the stored key (AD-7, NFR3)

*(Out of scope for this story: `tutorialSeen` has no producer anywhere in the codebase yet — no story has wired a "tutorial was completed" signal into the engine. Per the RESOLVED CONFLICT below, this story adds the field to `RunSnapshot` exactly as AD-4 specifies and always writes/reads it as `false`, since nothing else exists to set it truthfully. Wiring a real value is deferred to whichever future story first needs to consume it — do not invent tutorial-completion tracking here.)*

**RESOLVED CONFLICT (2026-08-01, story creation):** `tutorialSeen: Bool` is named explicitly by AD-4, the Consistency Conventions table, and this story's own epics.md AC #1 wording — it is a required field of the persisted shape, not optional. But `EXPERIENCE.md` states outright: "the story doesn't know whether the tutorial was seen" (no FR consumes this value), and no `TutorialView`/`HomeView` code anywhere sets any such flag today. Resolution: include the field in `RunSnapshot` (satisfies AD-4's Codable shape and keeps the persisted format forward-compatible so a later story doesn't need a schema migration to add it), hardcode it to `false` on every write, and do not attempt to read or branch on it anywhere. Flag this explicitly in Completion Notes so a future story wiring real tutorial tracking doesn't mistake `false` for a meaningful signal.

### Architecture compliance (AD-3, AD-4, AD-7)

- **AD-4** (`ARCHITECTURE-SPINE.md`#AD-4) is this story's primary spec — read it in full before starting. Key points already reflected in the ACs/Tasks above: exact field list and order, synchronous/immediate writes only (never debounced — the adversarial review's Finding 3 spells out exactly why: iOS can jetsam a backgrounded app before a debounce timer fires, silently losing pages), decode failure treated identically to "no snapshot," and clearing on reaching Ending (Finding 6 in the same review documents the exact bug — a completed run's snapshot never being cleared — that AC #5 exists to prevent).
- **AD-3**: `StoryRunEngine` remains the sole mutator of run state — persistence is a side effect *of* an intent completing, never a separate write path a View could trigger directly. Views never touch `UserDefaults` directly (Home's read via `RunSnapshotPresence` is a read-only presence check, not a mutation, and predates this story).
- **AD-7**: Swift Testing scope explicitly includes "`RunSnapshot` encode/decode round-trip" — this story is the first to actually exercise that clause of AD-7 for real (Stories 2.1–2.3 only asserted in-memory engine state).
- **Not in scope for this story**: `exitToHome()`/`restartRun()`/`startNewRun()` — AD-3 lists these as part of the engine's eventual full intent surface, but none exist as engine methods yet (`RootView`'s current "Exit to Home" is a temporary code-review addition that manipulates `NavigationPath`/`isPresentingStorySession` directly, not an engine intent). This story's AC #1 only names the three intents that exist today (`selectChoice`, `advancePage`, `goBack`) — do not add engine methods for the other three as part of this story; that's Story 2.7's job (Run Options Action Sheet) and possibly Epic 3 (Memory's `startNewRun`).

### Why `.ending` triggers a clear, not a write

The architecture's own adversarial review (`reviews/review-adversarial.md`, Finding 6) traces through exactly this scenario: without an explicit clear-on-Ending rule, a snapshot pointing at a finished run's terminal node persists forever, and Home's "whenever a run is in progress, show Resume Story" logic (driven by snapshot presence/decode-success) has no way to distinguish "genuinely in progress" from "finished, but the last-written snapshot still decodes fine." AD-4's own prose settles this explicitly: "reaching the Ending phase clears it (a completed run has nothing to resume)." AC #5 and Task 2 implement that rule directly at the point `currentNodeId` becomes an `.ending` node — which, given AD-6, happens the instant `selectChoice(_:)` or `advancePage()` moves onto a terminal node, with no separate "phase" concept to compute (the engine has no persisted `phase` field at all — Consistency Conventions and AD-4's field list are both exhaustive at four fields, and the adversarial review's Finding 7 on this point was resolved by *not* adding a phase field, deriving everything from `currentNodeId`'s node kind instead, consistent with AD-5's "phase is derived, not stored").

### Review Findings

- [x] [Review][Patch] Pre-existing `StoryRunEngineTests` write to real `UserDefaults.standard`, violating this story's own testing rule [ForkedEchoesTests/StoryRunEngineTests.swift:14-164] — every test that predates this story (`advancePageMovesFromReadingNodeToItsNext`, `selectChoiceRecordsHistoryAccumulatesScoreAndMovesToTarget`, `goBackMovesToThePreviouslyVisitedNode`, etc.) constructs its engine via the plain `StoryRunEngine(startingAt:)` initializer, which now defaults to `defaults: .standard`. Since every mutating intent calls `persistOrClearSnapshot()`, these tests silently write to and clear the real app's `UserDefaults.standard` domain — exactly what the story's own Testing Standards section says not to do ("do not have tests write to `UserDefaults.standard` directly, since that pollutes real app state and other tests"). Swift Testing also runs test methods concurrently by default, so several of these tests race each other over the same real key. This is the same class of bug the Completion Notes already document catching once for `resumingFromSnapshot` (Xcode/Simulator vs. Linux SwiftPM `.standard` persistence difference) — it's still present in the untouched pre-existing tests. **Fixed:** every test in the file now constructs its engine against its own isolated `freshDefaults()` suite.
- [x] [Review][Patch] `resumingFromSnapshot`/`loadValid` never reject a snapshot whose `currentNodeId` currently resolves to `.ending` [ForkedEchoes/Engine/RunSnapshot.swift:20-37, ForkedEchoes/Engine/StoryRunEngine.swift:46-55] — `loadValid` only validates `choiceHistory` entries against the current tree, never checking `currentNodeId` itself. A stale snapshot pointing at a node that a later content edit reclassified as `.ending` decodes as fully valid, resumes the engine sitting on a finished run, and `hasInProgressRun()` reports `true` — contradicting AC #5's "a finished run has nothing to resume." Once resumed there, no mutating intent runs again to clear it (advancing/selecting/going back are all no-ops on an `.ending` node), so the stale "in progress" state can persist indefinitely across relaunches. **Fixed:** `loadValid` now rejects any snapshot whose `currentNodeId` resolves to `.ending`, with new tests in both `RunSnapshotTests.swift` and `StoryRunEngineTests.swift` covering the rejection.

JSONEncoder().encode(snapshot) else { return }` neither clears the key nor retries. If encoding ever fails, a later cold launch resumes from the previously-written (now out-of-sync) snapshot rather than a clean fallback. **Fixed:** the encode-failure branch now removes the stored key instead of no-oping.
- [x] [Review][Patch] No test asserts that no-op guard-return paths skip persistence [ForkedEchoesTests/StoryRunEngineTests.swift — `advancePageIsNoOpOnANonReadingNode`, `selectChoiceOnANonChoiceNodeIsNoOp`, `goBackWithNoHistoryIsNoOp`, `advancePageIsBlockedOnAnUnresolvedChoiceNode`] — Task 2 requires these no-op paths to never call `persistOrClearSnapshot()`, but none of these tests check `UserDefaults` state before/after, so a regression that started writing on a no-op path would go undetected. **Fixed:** each of these tests now asserts `defaults.data(forKey: RunSnapshotPresence.runSnapshotKey) == nil` after the no-op call.
