# Story 2.9: Branch-Arrival Interstitial — First-Visit-Only Gate

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want the branch-arrival illustration to stay part of the story when I revisit that point,
so that re-reading doesn't lose the moment or force me through an artificial gate again.

*(Amendment to Story 2.6, raised via Sprint Change Proposal 2026-08-02 after Simulator playtesting — see `_bmad-output/planning-artifacts/sprint-change-proposal-2026-08-02.md` and `ARCHITECTURE-SPINE.md`#AD-5's 2026-08-02 amendment.)*

## Acceptance Criteria

1. **Given** a branch-arrival node visited for the true first time (not yet recorded as previously visited, surviving app relaunch — see Dev Notes' "Critical discrepancy" section for what this actually requires)
   **When** the player arrives
   **Then** phase derives to `.interstitial`: full-bleed illustration + caption renders as the node's permanent content (no separate ordinary-prose reveal), swipe/tap-zone do nothing, only Continue advances

2. **Given** a branch-arrival node already recorded as visited
   **When** the player arrives there again (backing up to it, or after an app relaunch)
   **Then** the identical illustration + caption renders, but swipe/tap-zone/back all behave like an ordinary page — no Continue-only gate

3. **Given** Story 2.6 shipped the original one-shot/prose-swap behavior
   **When** this story lands
   **Then** `ARCHITECTURE-SPINE.md` AD-5 and `EXPERIENCE.md`'s interstitial rows (already updated per the Sprint Change Proposal) match the shipped behavior, and Story 2.6's Swift Testing coverage is revised: no test may still assert the node reverts to ordinary body prose after dismissal

4. **And** a Swift Testing case verifies: a truly-first-ever visit to `.shoreArrival` derives `.phase == .interstitial`; after dismissal (one `advancePage()`), the SAME session's later `goBack()`/re-arrival at `.shoreArrival` derives `.phase == .reading` (not `.interstitial` again); and — the case this story exists to fix — an engine reconstructed via `resumingFromSnapshot(defaults:)` in a **fresh process** (a new `StoryRunEngine` instance, not the same one that dismissed it) onto a snapshot that has already passed through `.shoreArrival` once reports `.phase == .reading`, not `.interstitial`, even though the new instance's in-memory dismissal tracking starts empty (AD-4, NFR3)

5. **And** a manual-verification AC: in Xcode/Simulator, reach `.shoreArrival` for the first time and confirm the gated behavior (swipe/tap do nothing, only Continue advances); back up to the choice page and forward again to `.shoreArrival` in the *same session* and confirm it now behaves as an ordinary swipeable page (no Continue button, swipe/tap/back all work) while showing the identical illustration+caption; **force-quit and relaunch** the app so it resumes mid-run past `.shoreArrival`, then back up to `.shoreArrival` again and confirm it *still* renders as an ordinary swipeable page, not gated — this cross-relaunch case is the one Story 2.6 could not have tested and is the actual bug this story exists to close. Result + date recorded in Completion Notes List (project-context.md Process Agreement)

## Dev Notes

### Critical discrepancy — read this before Task 1

The Sprint Change Proposal (2026-08-02) and the already-applied `ARCHITECTURE-SPINE.md` AD-5 amendment both describe this story's implementation direction as "keyed off `visitedNodeIds`, which already exists and is already persisted per `RunSnapshot` (AD-4, in use since Story 2.5 for echo reachability) — no new persisted state needed." **This is not accurate against the current codebase, and taking it at face value will produce an implementation that passes every same-session test but still fails the actual relaunch case AC #2 requires.**

The real state, confirmed by reading the current source:
- `StoryRunEngine.visitedNodeIds` (`StoryRunEngine.swift:62`) is a `private var [NodeID]`, an ordered **back-navigation stack**, popped by `goBack()`. It is explicitly **not** part of `RunSnapshot` — `RunSnapshot.swift`'s own doc comment states "exactly these four fields, in this order, no more," and `resumingFromSnapshot(defaults:)`'s own doc comment (`StoryRunEngine.swift:76-79`) confirms "`visitedNodeIds` is not part of `RunSnapshot`... a resumed run starts with an empty back-navigation stack."
- The thing actually gating the interstitial today, `dismissedInterstitialNodeIds: Set<NodeID>` (`StoryRunEngine.swift:49`), is also **not persisted** — it's a private in-memory field, populated only by `advancePage()`'s Continue short-circuit within a running process, and reset entirely by `startFreshRunIfCurrentRunHasEnded()`. `resumingFromSnapshot(defaults:)` currently papers over this by inserting only the snapshot's own `currentNodeId` into this set on construction (`StoryRunEngine.swift:98`) — which happens to make "resume directly onto the arrival node" work, but does nothing for "the arrival node isn't `currentNodeId` at resume time, because the player has since moved past it" — exactly the case AC #2 describes ("backing up to it... after an app relaunch").
- Echo reachability (Story 2.5, `isEchoActive`) does not use `visitedNodeIds` at all — it's derived purely from `currentNodeId`'s node type (`StoryRunEngine.swift:27-32`). The Sprint Change Proposal's "in use since Story 2.5 for echo reachability" claim doesn't match this either.

Conclusion: this story genuinely needs new persisted state (or a persisted-data-derived equivalent) to satisfy AC #2 across a real relaunch — it is not the zero-schema-change refactor the planning docs describe. Task 1 above lays out the recommended path (extend `RunSnapshot`) and a fallback alternative (derive from `choiceHistory`). Pick one, implement it, and correct the architecture doc's claim as part of Task 5 rather than leaving a description that doesn't match what shipped — this project's own "Resolving doc conflicts" convention (project-context.md) says the most recent explicit decision wins and gets recorded, which is what Task 5 does here.
