# Story 3.2: Ending Screen

Status: done

## Story

As a player,
I want to see an ending screen that matches how my run concluded,
so that I understand how my choices resolved.

## Acceptance Criteria

1. **Given** a run reaches a terminal node (whether through ordinary branch traversal or a hard-fail gotcha choice), **when** the Ending phase is entered, **then** a single shared Ending template renders, differing only in outcome-specific text across home/stay/limbo/hard-fail (FR9), driven by that node's `EndingKind` (Story 3.1). [Source: epics.md#Story-3.2, AC1 — scoped to text, not illustration; see Dev Notes' "No illustration in this story" for why]
2. **Given** the Ending screen, **when** rendered, **then** the circuit Frame rests permanently in its powered-up ember state — a resting condition, not a transition (UX-DR7, DESIGN.md `components.ending-frame`). [Source: epics.md#Story-3.2, AC2]
3. **Given** the Ending screen, **when** the player taps anywhere, **then** the app advances past Ending — no auto-advance. [Source: epics.md#Story-3.2, AC3 — the real Memory destination is Story 3.3's job; see Dev Notes' "What 'advances to Memory' means in this story" for the required placeholder]
4. **Given** a hard-fail ending, **when** it renders, **then** it uses the same shared template with tone-appropriate dark-comedy copy, arriving directly from the gotcha choice rather than through normal page-turn flow (FR8, FR9). [Source: epics.md#Story-3.2, AC4]
5. **Given** the Ending screen's "tap to continue" affordance text, **when** rendered, **then** it is sourced from `Localizable.xcstrings`, consistent with the ending body copy's own per-node localization (AD-2). [Source: epics.md#Story-3.2, AC5]
6. **Given** the app is backgrounded or terminated while on the Ending or Memory screen, **when** it relaunches, **then** Home renders in its fresh-install "Start Story" state — `RunSnapshot` was already cleared on entering Ending (Story 3.1, AD-4), so there is no in-progress run to resume and no persisted recap to restore; this is expected, not a bug. [Source: epics.md#Story-3.2, AC6 — added by sprint-change-proposal-2026-08-05-epic-3-pre-review.md §4.5; no engine change required, only a Swift Testing/manual-verification assertion that this already holds]
7. **Given** the Ending screen's rendered content, **when** verified, **then** a Swift Testing case confirms each `EndingKind` produces the correct routed text (a node-authoring/content-plumbing check, per AD-7/NFR3's testing scope) and a manual Xcode/Simulator check confirms the permanently-active Frame, the tap-anywhere-to-advance gesture, and VoiceOver's accessible equivalent for it, recorded in this story's Completion Notes (project-context.md Pre-Creation Acceptance-Criteria Check).

## Dev Notes

### RESOLVED CONFLICT: Ending's eyebrow tag is in scope, unlike Story/Choice's

Story 2.8 explicitly ruled an eyebrow tag **out of scope** for Story/Choice reading pages (`2-8-reading-surface-visual-identity-dynamic-type-and-reduce-motion.md`'s "Scope Decision" section) — building one there would require a new `StoryNode` chapter/location field, a real content-model change AD-1 gates carefully, and epics.md's Story 2.8 AC never authorized it. **That reasoning does not apply here.** `mockups/ending.html` shows a small eyebrow-style tag ("Ending — Home" / "Ending — Hard-Fail"), but it needs zero new content fields — it's a pure function of the `EndingKind` that already exists on every `EndingPayload` (Story 3.1). Task 2 above is this story's version of the same "Content enum case → Views-layer presentation data" pattern `BranchArrivalInterstitialView.swift`'s private `BranchIllustration.assets` extension already establishes for branch illustrations — do not skip it by over-applying Story 2.8's precedent to a screen where the underlying blocker (missing content-model field) doesn't actually exist.

### No illustration in this story, despite epics.md AC #1's "text/illustration" wording

Epics.md's Story 3.2 AC #1 says the shared template differs "in outcome-specific text/illustration." **This story ships text only.** Evidence for this scope cut, checked directly against source docs rather than assumed:

- `mockups/ending.html` (the actual UX reference — `grep`ped directly, not summarized) contains **no image/illustration element at all** for either the Home or Hard-Fail variant — only the eyebrow chip, title, body copy, and continue-hint text inside the permanently-active frame.
- `DESIGN.md`'s `components.ending-frame` entry (the Components section's authoritative row for this screen) describes only the frame's permanent ember state — no illustration slot, no per-kind image token.
- Bundled illustration *production* (FR-12, `Resources/Assets.xcassets`) is explicitly Epic 4 Story 4.4 ("Branch-Reality Illustration Production") — no Ending-specific art assets exist yet, and inventing placeholder art here would be scope creep this story's AC doesn't actually require once checked against the real mockup.

If a future story (or a code-review finding) disagrees, that's a real design question for Sally/Winston, not an implementation default — don't silently add an illustration slot to `EndingPayload` to "match the AC wording" without that conversation, and don't silently skip flagging it either.

### What "advances to Memory" means in this story

Story 3.3 (Memory/Recap Screen) is the **next** story and does not exist yet — no `Views/Memory/` directory, no Memory-specific engine state. Epics.md's Story 3.2 AC #3 nonetheless requires "tap anywhere advances to Memory (Story 3.3)." This is the **exact same shape** of forward-reference Story 2.1 handled for the Ending screen itself before Story 3.1/3.2 existed (`StoryChoiceView.swift`'s `.ending` case rendered `Text(verbatim: "Run complete — Ending screen coming in Epic 3")`, tracked in `deferred-work.md:92` until this story replaces it). Task 4 above is this story's turn to do the same thing one phase later: add the `Phase.memory` case + transition (real engine work, since Story 3.3 needs it to already exist), but render only a placeholder for it (temporary, replaced wholesale by Story 3.3). Do **not** attempt to build any part of the real Memory screen (recap list, score/tier, Return Home/Start New Run) in this story — that's 100% Story 3.3's scope (epics.md#Story-3.3).

### `EndingView` should NOT reuse `StoryChoiceView`'s `readingComposition` gesture/button wiring

This is the single biggest structural decision in this story — see Task 3's inline reasoning for the full "why," but the short version: `RunOptionsButton` (Exit to Home / Restart / Exit and Clear Progress) has nothing meaningful to act on once a run has ended (`RunSnapshot` is already cleared, Story 3.1 AC #7 — "Exit to Home" would exit a run that no longer exists as an in-progress snapshot), and the swipe/tap-zone gestures conflict with AC #3's "tap **anywhere** advances" (a full-surface tap, not a left/right-third split). Build `EndingView` as its own top-level phase branch in `StoryChoiceView.body` (parallel to the existing `.interstitial` branch), not routed through `readingComposition`.

### `EndingPayload`'s field growth follows Story 3.1's non-defaulted-field precedent, not `.reading`'s defaulted one

Story 3.1 deliberately made `kind` non-optional/non-defaulted specifically so every terminal node's authoring site becomes a compile error until it supplies a value — this is what makes "every terminal node has a `kind`" a compiler guarantee (AD-1/AD-6). `titleKey`/`bodyKey` (Task 1) should follow the **same** non-defaulted pattern, for the same reason: a defaulted/optional field would let a future terminal node silently ship with placeholder/missing ending copy, exactly the class of bug AD-1's "no representable dead end" guarantee exists to prevent. Do not follow `.reading`'s `echoBodyKey`/`arrival` defaulted-parameter precedent here — that pattern is for genuinely *additive*, opt-in node features; ending text is not optional for an ending node.

### Existing tests/tree you must not break

`StoryTree.swift`'s 4 terminal-node cases (`.endingHomeward`, `.endingElsewhere`, `.endingLimbo`, `.endingHardFail`) and every path leading to them (`.boat`→`.boatEcho`, `.shore`→`.shoreArrival`, `.driftLimbo`, `.gotcha`) are untouched by this story except for the new `titleKey`/`bodyKey` arguments added to their `EndingPayload(...)` constructions — do not alter `NodeID`, `ChoiceOptionID`, targets, or `alignmentDelta`s. Run `swift test` immediately after Task 1's `EndingPayload` field addition (expect compile errors at all 4 call sites until fixed, by design) and again after Task 4's `Phase`/`advancePage()` changes, before writing any new tests, to confirm the existing 72 tests still pass unmodified in behavior (only the 4 `EndingPayload` construction sites should need edits).
