# Story 3.3: Memory / Recap Screen

Status: review

## Story

As a player,
I want a recap of every choice I made, what it caused, and my alignment score/tier after every run,
so that the run becomes a story about me.

## Acceptance Criteria

1. **Given** the Ending screen is tapped, **when** advancing, **then** Memory renders a read-only list of choice → consequence rows sourced from `RunSnapshot.choiceHistory` (in practice, `StoryRunEngine.choiceHistory` — the snapshot itself is already cleared by the time Memory renders, per AD-4/Story 3.1 AC #7), re-resolving display text from the current String Catalog by ID at render time — never stale frozen prose. [Source: epics.md#Story-3.3, AC1 — AD-4, UX-DR8]
2. **Given** any run, including hard-fail, **when** it completes, **then** Memory is shown for 100% of completed runs with no ending-type exception. [Source: epics.md#Story-3.3, AC2 — FR10]
3. **Given** the Memory screen, **when** rendered, **then** it shows the alignment score at the top in `{typography.stat}` styling — a purely reflective stat with no bearing on the ending already shown on the previous screen (closes FR7's display-only exposure rule from Epic 2's silent accumulation). [Source: epics.md#Story-3.3, AC3 — UX-DR8]
4. **Given** a descriptive tier label is derived from the score for display, **when** shown alongside the score, **then** it is cosmetic only — the tier label never changes or predicts which ending (Story 3.2) was already reached; the two are fully independent. [Source: epics.md#Story-3.3, AC4]
5. **Given** "Return Home" is selected, **when** activated, **then** the app navigates to Home; `RunSnapshot` was already cleared on entering Ending (AD-4), so no destructive confirmation is needed. [Source: epics.md#Story-3.3, AC5]
6. **Given** "Start New Run" is selected, **when** activated, **then** `startNewRun()` resets the engine to the initial node with cleared history/score and the app enters a fresh run — no confirmation required (AD-3). [Source: epics.md#Story-3.3, AC6]
7. **Given** a run that hard-failed on its very first choice (a `choiceHistory` of exactly one entry), **when** Memory renders, **then** it still shows a valid recap with that single choice-and-consequence row and the correspondingly small alignment score — no empty-state or crash at the minimum possible history length. [Source: epics.md#Story-3.3, AC7]
8. **Given** the Memory screen's "Return Home"/"Start New Run" action labels and any tier-label copy, **when** rendered, **then** every string is sourced from `Localizable.xcstrings` via generated symbols, never hardcoded (AD-2). [Source: epics.md#Story-3.3, AC8]
9. **Given** `scoreToTier(score:)` (AD-9), **when** the accumulated alignment score is negative, zero, or any value outside a placeholder band's current bounds, **then** it still resolves to exactly one tier — no unmapped/crash state — because the lowest band is open-ended. [Source: epics.md#Story-3.3, AC9 — added by sprint-change-proposal-2026-08-05-epic-3-pre-review.md §4.3]
10. **Given** the Memory screen's rendered content and its new engine-level surface (`startNewRun()`, `Tier.scoreToTier(score:)`), **when** verified, **then** Swift Testing cases cover the content-plumbing/tier-boundary/engine-intent logic named in AC #1/#6/#7/#9 (per AD-7/NFR3's testing scope), and a manual Xcode/Simulator check confirms the rendered recap, score/tier header, Return Home, and Start New Run — including VoiceOver and accessibility Dynamic Type — recorded in this story's Completion Notes (project-context.md Pre-Creation Acceptance-Criteria Check).

## Dev Notes

### Why Memory's rows always scroll, unlike Reading/Ending

`readingComposition` (`StoryChoiceView.swift`) and `EndingView` both reach for `ScrollView` *only* at accessibility Dynamic Type sizes, specifically because a `ScrollView`'s `UIScrollView`-backed pan gesture doesn't reliably cede to this app's own swipe-left/right page-turn `DragGesture` (Story 2.9's empirically-confirmed finding, documented in project-context.md's "SwiftUI gesture arbitration" section) — so those two screens avoid `ScrollView` at ordinary sizes purely to dodge that race, not because overflow can't happen there. **Memory has no competing gesture at all** — no swipe/tap-zone page-turning, no drag-based interaction of any kind — so there is no race to dodge, and no reason to withhold scrolling at ordinary Dynamic Type sizes. A real Epic 4 story tree could plausibly produce recap lists longer than one screen even at default text size, so Memory's rows should scroll unconditionally, following the same `GeometryReader`+`ScrollView` centering pattern project-context.md documents for Home/Tutorial (which also has no competing gesture) rather than the accessibility-conditional pattern the gesture-arbitration section warns future stories to read before writing code.

### `Tier` lives in `Engine/`, not `Content/` — unlike `EndingKind`

It's tempting to mirror `EndingKind`'s exact shape (a `Content`-layer enum, one case authored per terminal node) for `Tier`, since AD-9's own text says it "mirrors AD-6's `EndingKind` pattern." Resist that literal reading: `EndingKind` is fixed at **content-authoring time**, one value per `StoryNode` case — the compiler enforces its presence (AD-1). `Tier` is derived at **run time** from `alignmentScore: Int`, an `Engine`-owned field with no relationship to any specific `StoryNode` — there is no "terminal node" to author a `Tier` onto. What AD-9 actually asks for is the *single-source-of-truth pure-function* discipline `EndingKind`/AD-6 established, not the same file location or authoring mechanism. Keeping `Tier`/`scoreToTier(score:)` in `Engine/Tier.swift` is what keeps it inside this devcontainer's real `swift test` coverage (project-context.md Environment section: only `Engine`/`Content` are SwiftPM-tested here) — putting it in `Views/` (the way `EndingView.swift`'s private `EndingKind -> eyebrowKey` mapping stays Views-layer-only, since *that* mapping really is pure Content-derived display data) would make it untestable in this environment.

### `startNewRun()` vs. `startFreshRunIfCurrentRunHasEnded()` — two names for two callers, one shared reset

`RootView`'s `.onChange(of: isPresentingStorySession)` needs a *guarded* reset (`startFreshRunIfCurrentRunHasEnded()`'s existing "only if the current node is `.ending`" check) because it fires on every re-entry into the Story session, including resuming an in-progress run — an unconditional reset there would destroy live progress. Memory's "Start New Run" button, by construction, can only ever be tapped from `phase == .memory`, which is only reachable after `advancePage()` has already fired from a genuine `.ending` node — the guard condition is always already true by the time this button exists to be tapped. AD-3 names `startNewRun()` as its own distinct intent (not a synonym for the guarded method), so Task 3 adds it as the real "no-guard" reset entry point and has the older guarded method delegate to it, rather than either duplicating `resetRunState()`'s call or fabricating a redundant guard Memory's own phase-gating already makes unreachable.

### No dynamic per-run title on Memory, despite `mockups/memory.html`'s `<h1>`

Same shape as Story 3.2's "no illustration despite AC wording" scope cut: `mockups/memory.html` shows a generated-sounding title ("The Long Way Home") above the score, but no field anywhere in `Content`/`Engine` supplies per-run title text, no epics.md AC for this story mentions a title, and inventing one (a `StoryTree`-wide static string? a runtime-generated summary?) would be a real, undiscussed content-model decision this story's AC doesn't authorize. Ship the static "Your Run" eyebrow (zero content-model cost, matches the mockup's chrome) and stop there — flag the missing per-run title as an open design question for Sally/Winston if it resurfaces, don't silently invent a mechanism for it here.

### Consequence text lives on `ChoiceOption`, not on the *target* node

It might seem more natural to source "what a choice caused" from the node it leads to (e.g. `.boatEcho`'s `bodyKey`) rather than adding a new field directly on `ChoiceOption`. Don't do this: a target node's `bodyKey` is that node's *own* reading-page prose, written to read naturally as the next page a player advances through mid-run — reusing it verbatim as a retrospective "here's what that caused" summary on Memory would either read oddly out of context or require an entirely separate summarization step at render time. A dedicated `consequenceKey` directly on the edge (`ChoiceOption`, alongside the existing `labelKey`/`alignmentDelta`) keeps this exactly as simple as `EndingPayload`'s `titleKey`/`bodyKey` precedent: one new authored field, one new compile-time-enforced call site per option, no runtime text transformation.

### Existing tests/tree you must not break

`StoryTree.swift`'s 4 terminal-node cases and all paths to them are untouched by this story except for the new `consequenceKey` argument added to `.firstChoice`'s 4 `ChoiceOption(...)` constructions — do not alter `NodeID`, `ChoiceOptionID`, `EndingKind`, `EndingPayload`, targets, or `alignmentDelta`s (all Story 3.1/3.2 territory). Run `swift test` immediately after Task 1's `ChoiceOption` field addition (expect compile errors at all 4 call sites until fixed, by design) and again after Tasks 2/3's new engine-adjacent code, before writing any new tests, to confirm the existing 76 tests (as of Story 3.2) still pass unmodified in behavior.

### Architecture citations

- **AD-1** (content structure is a compiled Swift tree): `ChoiceOption.consequenceKey`'s non-defaulted-field shape (Task 1) mirrors `EndingPayload.titleKey`/`bodyKey`'s (Story 3.2) — see the dedicated Dev Notes section above.
- **AD-2** (prose/text lives in `Localizable.xcstrings`, referenced by plain dot-path `String` keys, boxed as `LocalizedStringKey` at the `Text(_:)` call site): applies to every new key this story adds (`story.firstChoice.choice.<n>.consequence`, `memory.eyebrow`, `memory.tier.*`, `memory.returnHome`, `memory.startNewRun`).
- **AD-3** (`StoryRunEngine` is the sole mutator of run state; explicit intent-method surface including `startNewRun()`): Task 3 adds the literal method AD-3 already names — do not invent a differently-named method or bypass the engine from the View.
