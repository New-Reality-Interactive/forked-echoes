As a player using any assistive technology,
I want the complete app — Home through Memory — verified end-to-end for accessibility structure, Dynamic Type, Reduce Motion, and contrast,

This is Epic 3's closing accessibility/contrast pass, deliberately sequenced **after** Story 3.6 (Reading & Ending Surface Background and Frame Inset Rule) so it validates the corrected screens rather than needing a redo — Story 3.6 is `done` as of 2026-08-07, so this ordering now holds cleanly. This story also closes out four specific accessibility items that individual story code reviews flagged and explicitly deferred to it, rather than fixing them locally out of scope at the time:

- **Story 2.8 code review (2026-08-02):** `runOptionsButtonClearance` (a fixed 60pt constant) was never re-verified at the largest accessibility Dynamic Type category (AX5) — deferred here (AC7).

Unlike the app's other stories, this one is **audit-and-fix**, not build-new-feature: most ACs describe a systematic verification pass across the *entire* app (Epics 1-3), not a single screen or component. Expect most of the work to be reading/inspecting existing code and exercising the Simulator, with code changes only where the audit surfaces an actual gap.

## ⚠️ Critical Context: This Is a Full-App Audit, Not a New-Screen Story — Read Before Starting

Every other Epic 1-3 story has scoped its own accessibility work locally (VoiceOver labels, Dynamic Type scaling, tap targets) as part of building that screen. This story's job is to **walk the seams between those stories** — the places a screen-local pass wouldn't have caught: the full Home→Tutorial→Story→Choice→Interstitial→Ending→Memory path exercised as one continuous VoiceOver-only session, one continuous Reduce-Motion run, and one continuous max-Dynamic-Type pass, plus two specific formal-verification gaps (AC10) and two specific reachability judgment calls (AC7-AC9) that prior code reviews already scoped precisely.

### The exact behavioral contract this story is auditing against (EXPERIENCE.md's Accessibility Floor)

This is the authoritative behavioral spec — read it before starting the audit, don't re-derive expected behavior from code alone:

> - VoiceOver: every choice card exposes role + label + state ("Choice, Ask Sam about the boat, not yet selected" / "...selected, double-tap again within 1.5 seconds to undo"). Double-tap activates immediately — VoiceOver users are never asked to sustain a 3-second hold; the instant-commit-plus-undo-window path (identical to a quick tap) is the VoiceOver-compatible equivalent required by FR-11. The Story page additionally exposes "Next Page"/"Previous Page" as VoiceOver custom actions (rotor-accessible), since a one-finger swipe is otherwise consumed by VoiceOver's own navigation and never reaches the app. The run-options button carries an explicit `accessibilityLabel` of "Run options" (not left to the SF Symbol's default name).
> - Dynamic Type: honored through `DESIGN.md` typography tokens at every role, each bound to a named iOS text style rather than a manual scale multiplier; body/echo text must grow through accessibility sizes without truncation — layout absorbs the growth, type never clamps.
> - Reduce Motion: skip the choice-card charge-fill animation (commit is instant instead, no 3s wait) and skip the frame's echo power-up glow/transition (ember state + shape cue apply immediately, no transition). Page-turn and the branch-arrival interstitial's entrance/exit — both plain wayfinding motion under normal conditions — collapse to an instant cut; nothing in the system produces continuous or looping motion under Reduce Motion.
> - Tap targets ≥ 44pt on every interactive element, including choice cards, page tap zones, the run-options button, and the Home/Tutorial/Ending/Memory actions.
> - Focus traversal follows reading order — eyebrow tag → prose → choices → pager — on every Story/Choice page; the run-options button sits last in traversal order so it never interrupts reading flow.
> - The Restart confirmation uses the platform's native destructive-action pattern (system alert/action sheet) — inherits VoiceOver announcement and Dynamic Type behavior for free; no custom-built confirmation dialog.

### AC10: WCAG 1.4.11 non-text contrast — pre-computed reference values (verify against real rendering, don't skip the Simulator/Instruments check)

Two pairs need formal 1.4.11 verification (3:1 threshold for graphical objects/UI components, distinct from 1.4.3's 4.5:1 text threshold):

1. **`SecondaryActionButtonStyle`'s border stroke** (`ButtonStyles.swift`): `Color.inkPrimary` stroke, `ButtonMetrics.borderWidth` (3px), on whatever background sits behind it (transparent button, so effectively `surfaceBase`/`surfaceRaised` depending on call site).
2. **Memory row divider** (`components.memory-row.divider-color` = `{colors.trace-brass}`, `MemoryView.swift`): per Story 3.6's resolved conflict, Memory rows render on `surfaceBase` (not `surfaceRaised` — no separate card fill), so the real pairing is `trace-brass` on `surface-base`.

Computed from this codebase's actual `Assets.xcassets` sRGB values (relative-luminance method, same method DESIGN.md's existing table uses) as a starting reference — confirm these against the real rendered Simulator/Instruments contrast check rather than trusting the arithmetic alone, since DESIGN.md's own table is the project's source of truth once updated:

| Pair | Light | Dark | Threshold |
|---|---|---|---|
| `ink-primary` border on `surface-base` | ~15.6:1 | ~15.1:1 | 3:1 (1.4.11) |
| `ink-primary` border on `surface-raised` | ~16.8:1 | ~13.7:1 | 3:1 (1.4.11) |
| `trace-brass` (memory-row divider) on `surface-base` | ~4.4:1 | ~7.9:1 | 3:1 (1.4.11) |

All four clear 3:1 with substantial margin — this audit is expected to be a formal confirmation, not a bug hunt, but do the check for real (don't skip it because the arithmetic looks safe) and record the actual verified numbers/method in Completion Notes so DESIGN.md's contrast table can cite them.
