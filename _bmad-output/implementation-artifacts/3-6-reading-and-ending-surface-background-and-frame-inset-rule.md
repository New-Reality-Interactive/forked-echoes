# Story 3.6: Reading & Ending Surface Background and Frame Inset Rule

Status: review

## Story

As a player,
I want the Reading, Ending, and Memory surfaces to render on the app's warm paper-cream/raised-card background and the circuit frame to show its inset rule line,
so that these screens match DESIGN.md instead of falling back to the plain system default background with a partially-drawn frame.

## Acceptance Criteria

1. **Given** DESIGN.md's `{colors.surface-base}`/`{colors.surface-raised}` background tokens, **when** `StoryChoiceView.swift` (reading/interstitial), `FrameView.swift`, `EndingView.swift`, `MemoryView.swift`, and `RootView.swift` are inspected, **then** each screen renders against the correct token exactly once — a single decision is made and documented (Dev Notes) on whether the background is applied once at an outer container (`StoryChoiceView`/`RootView`) or locally per-view, avoiding duplicate or conflicting `.background(...)` calls across the chain. [Source: epics.md#Story-3.6, AC1]
2. **Given** `components.frame`'s `inset-rule-width`/`inset-rule-color`/`inset-rule-color-active` tokens, **when** `FrameView` renders in both dormant (brass) and powered-up (ember) states, **then** a stroked rule inset from the card edge is drawn at the correct width/color per state, distinct from and in addition to the existing corner via/pad marks. [Source: epics.md#Story-3.6, AC2]
3. **Given** light and dark theme, **when** the new background and inset-rule colors render, **then** all text/color pairs affected continue to meet WCAG AA thresholds per DESIGN.md's verified contrast table (NFR7) — no new pairing introduced outside that table. [Source: epics.md#Story-3.6, AC3 — NFR7]
4. **Given** Dynamic Type at an accessibility size, **when** the corrected background/inset-rule renders on Reading, Ending, and Memory, **then** no text is clipped or truncated as a side effect of the change (FR11, NFR8). [Source: epics.md#Story-3.6, AC4 — FR11, NFR8]
5. **And** a manual-verification AC: in Xcode/Simulator, confirm the correct background tone and a visible inset rule line on Reading, the branch-arrival interstitial, Ending, and Memory, in both light and dark appearance, at default and an accessibility Dynamic Type size. Result + date recorded in the story's Completion Notes List. [Source: epics.md#Story-3.6, AC5 — project-context.md Process Agreement; no engine logic is touched by this story, so this is a manual-verification AC, not a Swift Testing AC per project-context.md's Pre-Creation Acceptance-Criteria Check]

## Background: Why This Story Exists

Added via Story 3.4's code review follow-up (2026-08-06) — see `deferred-work.md`'s "code review of 3-4-ending-and-memory-visual-identity" entry. Two token gaps, both tracing back to Story 2.5 (pre-dating Story 3.4) and both living in `FrameView.swift`, bundled into one story per the reviewer's own note:

1. **`{colors.surface-base}`/`{colors.surface-raised}` is never applied via `.background(...)` anywhere in the Reading→Ending→Memory chain.** `StoryChoiceView.swift`, `FrameView.swift`, `EndingView.swift`, `MemoryView.swift`, and `RootView.swift` all render on the system default background instead. Only `HomeView.swift`/`TutorialView.swift`/`ChoiceCardView.swift` apply `surfaceBase`/`surfaceRaised` today.
2. **`components.frame`'s `inset-rule-width`/`inset-rule-color`/`inset-rule-color-active` (a 1px stroked border line around the card, distinct from the corner via/pad marks) is never drawn.** `FrameView.swift` only renders the four corner marks (`GeometryReader` + `ForEach(Corner.allCases)`).

Sequence this story **before Story 3.5** (End-to-End Accessibility Validation) so 3.5 validates the corrected screens rather than needing a redo — 3.5 is currently `backlog` and unstarted, so this ordering holds.

## ⚠️ Critical Context: A Design Decision Is Baked In Below — Read Before Coding

This story's AC #1 explicitly requires "a single decision is made and documented (Dev Notes) on whether the background is applied once at an outer container... or locally per-view." **That research has already been done for you** by tracing the actual DESIGN.md mockup source files (not just the token table) — read this section fully before touching code; it tells you exactly where the two background colors go and why, so you don't have to re-derive it.

### Evidence from the mockup source (`mockups/story-choice-warm-ink-circuit.html`, `ending.html`, `memory.html`)

- `.screen` (the whole device viewport) has `background: var(--bg)` = **`surface-base`**.
- `.frame-well` (the reading card — the entire content region wrapped by the circuit frame's corner marks) has `background:#fff` = **`surface-raised`**, and is full-bleed within its container (`height:100%`, no visible `surface-base` margin around it in practice).
- `.frame-well::before` is the **inset rule**: `content:""; position:absolute; inset:9px; border:1px solid var(--trace-idle)` (dormant) / `border-color:var(--frame-active); box-shadow:inset 0 0 0 1px var(--frame-active)` (active/ember, `ending.html`). **`inset:9px` matches `LayoutMetrics.frameCornerInset` (`Spacing.small + 1` = 9pt) exactly** — the same inset the corner via/pad marks already center on. Width is 1px = DESIGN.md's `inset-rule-width`.
- `memory.html`'s `.screen` background is `var(--bg)` = `surface-base`; its `.row` class (`padding:14px 0; border-bottom:1px solid var(--trace-idle)`) has **no background of its own** — rows render directly on the page's `surface-base`, not a separate raised card. This is a real tension against DESIGN.md's token table, which names `memory-row.background: '{colors.surface-raised}'` — see "RESOLVED CONFLICT" below.

### The single decision (implement exactly this; document it in Dev Notes when done)

**`surfaceBase` — applied once, at `StoryChoiceView.body`'s outermost `Group`** (the one that switches between `.ending`/`.memory`/`.interstitial`/`readingComposition`), as `.background(Color.surfaceBase.ignoresSafeArea())` — same call shape `HomeView.swift`/`TutorialView.swift` already use. This one call site covers all four phase branches (Reading/Choice, interstitial, Ending, Memory) because they all render through this shared `Group`.

- **`RootView.swift` needs no direct background change.** Its own body has no bare content — `NavigationStack` hosts `HomeView`/`TutorialView` (which already own their own `surfaceBase` background) and `.fullScreenCover` hosts `StoryChoiceView` (which will own it after this story). Inspect it per AC #1, confirm this, and say so explicitly in Dev Notes/Completion Notes — do not add a redundant `.background(...)` call there.
- **`MemoryView.swift` needs no direct background change either** — it renders through `StoryChoiceView`'s `Group` and inherits the new background from there. Inspect it per AC #1, confirm, document — don't duplicate.
- The interstitial branch (`BranchArrivalInterstitialView`, rendered when `engine.phase == .interstitial`) already paints its own full-bleed, fully opaque `Color.surfaceInverse` background (`BranchArrivalInterstitialView.swift:77`, sized via `.frame(maxWidth: .infinity, minHeight: availableHeight)` from its own `GeometryReader`) — confirm during Task 4's manual pass that the new `surfaceBase` sitting behind it never bleeds through (it shouldn't; it's fully occluded), but do not modify `BranchArrivalInterstitialView.swift` — DESIGN.md's `interstitial.background` token is already correctly wired there and is out of this story's scope.

**`surfaceRaised` — applied once, inside `FrameView` itself**, as a full-bleed fill sized to the same area the corner marks span, added alongside (not replacing) the existing `GeometryReader`/`ForEach` corner-mark rendering, still under the existing `.allowsHitTesting(false)`/`.accessibilityHidden(true)` modifiers so gesture/VoiceOver behavior on the content beneath it is unaffected. This is the correct single location because:

- `frame.background` (DESIGN.md) is a property of the frame *component*, and `ending-frame` explicitly `inherits: '{components.frame}'` — one component owns the token, matching this codebase's existing "one component, one place" pattern (e.g., `FrameView` already owns both dormant and active corner-mark rendering for every screen that uses it).
- `FrameView` already has exactly two call sites — `StoryChoiceView.swift`'s `readingComposition` (`.overlay { if isFrameEligibleNode { FrameView(...) } }`) and `EndingView.swift` (`.overlay { FrameView(isActive: true) }`) — both already size their content to `maxWidth: .infinity, maxHeight: .infinity` before the overlay, so `FrameView`'s own full-bleed fill will exactly match. Fixing it in `FrameView` fixes both screens in one place, with no separate `.background(Color.surfaceRaised)` call needed in either `StoryChoiceView.swift` or `EndingView.swift`.
- `Memory` never uses `FrameView` (DESIGN.md/`mockups/memory.html` and this codebase's existing `MemoryView.swift` header comment are explicit: "no circuit frame" on Memory), so it correctly never gets this fill — Memory's only background is the `surfaceBase` it inherits from `StoryChoiceView`, matching the mockup evidence above.

**Net effect once both are wired:** Reading/Choice and Ending render edge-to-edge on `surfaceRaised` (via `FrameView`'s new fill, which visually covers the `surfaceBase` sitting behind it at the `StoryChoiceView` level — this is expected and correct, not a conflict, since the mockup's `.frame-well` is itself full-bleed within its screen). The interstitial renders on `surfaceInverse` (unchanged, already correct, fully opaque). Memory renders on `surfaceBase` alone (matching the mockup, no separate card fill). This is "applied exactly once" per screen in the sense AC #1 asks for: no view ever has two competing `.background(...)` calls layering the same region, and every visible pixel traces to exactly one deliberate token choice.

### RESOLVED CONFLICT (record this verbatim in Dev Notes, per project-context.md's "Resolving doc conflicts" convention)

DESIGN.md's `components.memory-row.background` names `'{colors.surface-raised}'`, but `mockups/memory.html`'s actual `.row` CSS has no background at all — rows render directly on the page's `surface-base`. Per project-context.md's precedent (the most recent explicit decision wins and gets recorded, not silently picked), this story's decision is: **follow the mockup — Memory's rows get no separate `surfaceRaised` fill.** Do not add one as a side effect of this story. If a future story wants to formally revisit this (e.g., give rows an explicit raised card treatment), it should do so deliberately with its own AC, not as an incidental interpretation of this story's background work.
