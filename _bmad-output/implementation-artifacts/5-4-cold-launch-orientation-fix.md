# Story 5.4: Cold-Launch Orientation Fix

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want the app to render in the correct layout the moment it launches, regardless of which orientation my device is already in,
so that I never see a wrong, stretched, or clipped layout that only corrects itself after I rotate my device.

## Acceptance Criteria

1. **Given** the device is already rotated to landscape before the app is launched, **when** Home first renders, **then** it renders the landscape layout immediately, with no portrait-then-landscape flash and no rotation required to self-correct. [Source: epics.md#Story 5.4]
2. **Given** the device is already in portrait before the app is launched, **when** Home first renders, **then** it renders the portrait layout immediately (regression guard — confirms the fix doesn't invert the bug for the other starting orientation). [Source: epics.md#Story 5.4]
3. **Given** the fix is in place, **when** either cold-launch case is exercised in the Simulator, **then** the result is recorded in this story's Completion Notes List (date + orientation(s) checked), per the verification-reporting agreement adopted 2026-07-26. [Source: epics.md#Story 5.4, deferred-work.md#PROCESS item]

## Dev Notes

- **What this story actually fixes:** Neither `HomeView.swift` nor `TutorialView.swift` currently branch on `verticalSizeClass` at all (confirmed by reading both files) — Story 5.3 deliberately kept both geometry-only (`GeometryReader` + static `.frame(maxWidth:)` caps from `LayoutMetrics`), per AD-8's "no-op in portrait" rule. That means the reported cold-launch bug is not a missing/wrong size-class branch — it's that `GeometryReader`'s **very first** layout pass after a cold launch can report stale/incorrect bounds when the device was already rotated before the app opened (a real, user-confirmed, reproducible defect — see `deferred-work.md`'s "sprint demo" follow-up, not a platform limitation the team has decided to accept). [Source: ForkedEchoes/Views/Home/HomeView.swift, ForkedEchoes/Views/Tutorial/TutorialView.swift, _bmad-output/implementation-artifacts/deferred-work.md#Follow-ups from: sprint demo]
- **Why the fix is a one-shot `UIWindowScene.interfaceOrientation` read, not `UIDevice.orientation`:** AD-8 explicitly bans `UIDevice.orientation`/`UIDeviceOrientationDidChangeNotification` as an *ongoing structural layout signal* ("brittle... doesn't map cleanly onto SwiftUI's declarative environment model and requires manual lifecycle handling") and bans `horizontalSizeClass` (ambiguous on standard iPhones). It does **not** ban a single, one-time authoritative read of the window scene's `interfaceOrientation` used only to correct the first stale layout pass before paint — that's a narrower, bounded operation, not a persistent observer or a second orientation-detection mechanism running alongside `verticalSizeClass`. Do not introduce a `NotificationCenter` subscription or any repeated polling — if the implementation ends up looking like continuous observation, it has drifted into exactly what AD-8 prohibits and needs to be rethought as a single corrective check at `.onAppear`/`.task` instead. [Source: _bmad-output/planning-artifacts/architecture/architecture-game-2026-07-25/ARCHITECTURE-SPINE.md#AD-8]
- **If Simulator verification shows the fix isn't taking effect, don't reach for `NotificationCenter` — try deferring the toggle instead.** The bug's root cause is UIKit's window bounds settling shortly after mount; if the corrective `@State` toggle fires synchronously within the same `.onAppear` tick, the forced re-layout could still observe the same stale bounds. Before concluding the one-shot-read approach is wrong, try deferring the toggle by one runloop tick (`DispatchQueue.main.async`) — that's still a bounded, one-time correction, not a persistent observer, so it stays compliant with AD-8.
- **Build it once, reusably — don't patch `HomeView.swift`/`TutorialView.swift` independently.** epics.md's own downstream note flags that Epic 2's reading-surface pager will reuse this same `GeometryReader`-based centering pattern and "would otherwise inherit the bug" if this story doesn't produce something reusable. Put the fix in a new `Views/DesignSystem/` file as a `View` extension modifier (matching the existing shared-component convention: `ButtonStyles.swift`, `LayoutMetrics.swift`, `Typography.swift` all live there), not as duplicated inline code in each screen. [Source: _bmad-output/planning-artifacts/epics.md#Story 5.4 downstream note]
- **Only `HomeView.swift` has a literal cold-launch bug to fix; `TutorialView.swift` is applied for consistency/prevention, not because it was independently reproduced.** `RootView.swift` always starts its `NavigationStack` at `HomeView` — there's no state restoration or deep link that lands a player on Tutorial at cold launch. Say this plainly in Completion Notes so the record doesn't overclaim a second verified bug. [Source: ForkedEchoes/Views/RootView.swift]
- **Orientation lock is already lifted in both Debug and Release** (`INFOPLIST_KEY_UISupportedInterfaceOrientations = "UIInterfaceOrientationPortrait UIInterfaceOrientationLandscapeLeft UIInterfaceOrientationLandscapeRight"` in `project.pbxproj`, both configs) — Story 5.2 already did this; nothing to change here. [Source: ForkedEchoes.xcodeproj/project.pbxproj]
- **No design-token Swift layer beyond `LayoutMetrics`/`Spacing`/`ButtonMetrics`** — if the fix needs any numeric/timing constant (unlikely, but e.g. a debounce), follow Story 1.6's convention: a descriptively-named constant in `LayoutMetrics.swift` or a new small enum in the new file, never a bare literal. This story is not expected to need any new DESIGN.md-traceable value since it's pure launch-timing logic, not visual layout.
- **No Xcode/macOS toolchain (`xcodebuild`, Apple SDKs, Simulator) in this devcontainer** — implementation here is hand-authored to spec. Unlike earlier stories, a Linux Swift toolchain (`swiftc`) is now present, so real parser-level syntax validation (`swiftc -parse`) is available and should be used per Subtask 3.1, but `UIKit`/`SwiftUI` still don't resolve here, so no actual compilation or UI verification is possible. Actual Simulator cold-launch verification in both orientations is mandatory before this story can be considered done and must be recorded per AC #3/Subtask 3.2 — do not mark this story `done` without that confirmation logged in Completion Notes.
