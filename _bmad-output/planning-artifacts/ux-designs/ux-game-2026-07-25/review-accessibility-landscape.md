# Accessibility Review — Landscape Addition (Sprint Change Proposal, 2026-07-26 / Epic 5)

Reviewed: DESIGN.md and EXPERIENCE.md's new landscape content only (`components.reading-surface`, `frame`/`choice-card` landscape notes, new Layout & Spacing landscape paragraph, new Do/Don't rows, "Responsive & Platform" section incl. both `[ASSUMPTION]` tags, updated Foundation line), against `review-accessibility.md`'s portrait-pass baseline, and the 3 new landscape mockups (`home-landscape.html`, `tutorial-landscape.html`, `story-choice-landscape.html`) diffed against their portrait counterparts (`home.html`, `tutorial.html`, `story-choice-warm-ink-circuit.html`).

## Overall verdict

The landscape spine text is conceptually sound (frame/behavior "unchanged, just reflows," reading column capped, choice cards row instead of stack). But the actual reference mockups meant to compose/validate that text contain a **concrete, measurable violation of the pre-existing 44pt tap-target floor** in real interactive elements (not decorative scaffolding), present at *default* text size, on all three new mockups — this isn't a Dynamic-Type-growth risk, it's already failing in the artifact as authored. The Dynamic Type headroom claim also doesn't visibly survive the transition to landscape's shorter frame-well. These need fixing before this pair is landscape-build-ready.

## Findings

- **critical** — Real interactive elements in all 3 new landscape mockups compute below the 44pt minimum tap target, at default (non-accessibility) Dynamic Type size.
  *Violates/risks:* EXPERIENCE.md's Accessibility Floor: "Tap targets ≥ 44pt on every interactive element, including choice cards ... and the Home/Tutorial/Ending/Memory actions" — a requirement the review brief itself notes is already established, non-negotiable, and orientation-agnostic (nothing scopes it to portrait only).
  *Concrete evidence (CSS as authored, padding + font-size, default browser line-height ≈1.2):*
  - `home-landscape.html` `.btn`: `padding:12px 20px; font-size:15px` → ≈12+18+12 = **~42px** tall (portrait `home.html` `.btn` at `padding:16px 20px; font-size:16px` ≈51px — comfortably clears the floor; landscape's shrink is what breaks it).
  - `tutorial-landscape.html` `.btn`: `padding:10px 16px; font-size:14px` → ≈10+16.8+10 = **~36.8px** tall (portrait `tutorial.html` `.btn` at `padding:15px 16px; font-size:17px` ≈50.4px).
  - `story-choice-landscape.html` `.choice` for any short, non-wrapping label (e.g. "Follow Sam.", "Call out first." — both fit on one line at 13px in the ~166–190px-wide 3-up column): `padding:12px 12px; font-size:13px`, single line → ≈12+15.6+12 = **~39.6px** tall (portrait's full-width `.choice` at `padding:15px 16px; font-size:17px` clears 44pt easily; only choice text long enough to wrap to 2+ lines rescues the landscape card, which is not guaranteed and isn't a property the spec asserts).
  This is a systemic pattern (3 of 3 new mockups), not a one-off typo: the mockups uniformly shrank both padding *and* font-size to make content fit the shorter landscape height, and in doing so silently dropped below the floor for the real, tappable controls — not the "margin"/tight-fit dev-annotation text, which is correctly exempt.
  *Fix:* Add an explicit `min-height: 44pt` (or an equivalent min-tap-target token) to `components.choice-card` and to the Home/Tutorial action button spec that applies regardless of orientation or content length, and correct the three landscape reference mockups to match it (increase padding back up, or keep font-size at the real token value — see next finding — so height is no longer solely dependent on whether the label wraps).

- **high** — Dynamic Type headroom claim doesn't visibly survive landscape's shorter frame-well, and the compounding risk EXPERIENCE.md itself flags is unvalidated anywhere.
  *Violates/risks:* DESIGN.md's Layout & Spacing headroom paragraph ("the frame-well's padding and the circuit corner assembly's clearance are specified with generous fixed headroom... sized to the *largest* accessibility Dynamic Type category") was validated in portrait via `mockups/story-choice-three-way.html`'s accessibility-scale stress test. Landscape has no equivalent: `story-choice-landscape.html`'s "3-choice/tight-fit" case — the one state explicitly called out as the risk in EXPERIENCE.md's `[ASSUMPTION]` — renders at default text size only (mockup font-sizes are static px, not simulating an accessibility content-size category). Meanwhile the landscape mockups themselves reduce the frame-well's vertical padding relative to portrait (`story-choice-landscape.html`: `padding:18px 26px` vs. portrait's `padding:26px 18px 16px`; `tutorial-landscape.html`: `padding:20px 28px` vs. portrait's `26px 18px 16px`) — i.e. exactly the dimension (vertical clearance under/around the fixed 30×30px corner geometry) that the headroom rule depends on shrinks in the orientation with the least vertical room to begin with, and DESIGN.md's headroom paragraph never states a landscape-specific value or explicitly reconfirms the portrait-derived headroom still holds.
  *Fix:* Either (a) produce a landscape equivalent of `story-choice-three-way.html` (3-choice + accessibility-scale text, at the actual capped column width) before treating landscape headroom as validated, or (b) if landscape's frame-well padding is intentionally smaller than portrait's, state that explicitly in DESIGN.md and show the headroom math/mockup still clears the largest accessibility category at that smaller padding.

- **high** — The "3-card row may feel tight on SE" `[ASSUMPTION]` understates the actual risk and should become a measurable, hard constraint rather than a deferred implementation judgment call.
  *Violates/risks:* EXPERIENCE.md's Responsive & Platform assumption frames this as a fit/cosmetic concern ("may feel tight... flagged for validation during implementation"). The real mechanism is worse: per-card width in a 3-up row is fixed at roughly a third of the capped reading column regardless of Dynamic Type category, so as accessibility text grows, each card is forced into progressively more line-wraps precisely on a control that *gates forward progress* (a choice must resolve before the player can continue) — in the one orientation with the least vertical headroom to display the result. Combined with the previous finding (no accessibility-scale landscape mockup exists), the actual worst case is untested. Note also that the mockup used to depict this "tight-fit" case is built at 852×393pt (iPhone 14/15 Pro-class landscape dimensions) — not the ~667×375pt SE landscape size the assumption explicitly names as the risk — so even the default-size "validation" doesn't depict the smallest real device.
  *Fix:* Replace "flagged for validation... if it doesn't fit cleanly" with a measurable trigger for the 2+1 fallback (e.g., "switch to 2+1 wrap once the longest choice label would wrap beyond N lines at the current column width," or "trigger 2+1 at content size ≥ accessibility-M / at screen widths ≤ X pt"), and treat it as an acceptance criterion for Story 5.3 rather than an open, implementation-time-only judgment call. Also rebuild (or add to) the tight-fit mockup at true SE landscape dimensions (667×375pt) with accessibility-scale text, not just the larger Pro-class device at default size.

- **medium** — Reference mockups' actual reading-column max-width doesn't match the `column-max-width-landscape` token value.
  *Violates/risks:* DESIGN.md sets `components.reading-surface.column-max-width-landscape: 680px`, but the mockups meant to compose/validate it use different, narrower values: `story-choice-landscape.html` `.reading-column{max-width:520px}` and `tutorial-landscape.html` `.reading-column{max-width:480px}`. Neither matches 680px. As a token value in isolation, 680px is reasonable — at `{typography.body}` (20px/500 SF Pro), that's roughly 60–70 characters per line, squarely inside the stated 60–75cpl target — so this isn't a case of the spec's number being wrong; it's the "authoritative" mockups silently disagreeing with the spec's own token, which risks an engineer building to whichever one they read first.
  *Fix:* Update the two mockups' `.reading-column` max-width to 680px (or explicitly annotate in-mockup why a narrower illustrative value was chosen, if intentional), so the token and its reference artifacts agree.

- **medium** — VoiceOver traversal order for the new horizontal choice row is never explicitly stated, leaving an invariant undocumented.
  *Violates/risks:* EXPERIENCE.md's Accessibility Floor states traversal order for a Story/Choice page ("eyebrow tag → prose → choices → pager") but says nothing about the order *among* choice cards once they reflow from a vertical stack to a horizontal row. In the actual `story-choice-landscape.html` markup the three choice `<div>`s stay in the same document order as portrait (so VoiceOver's default left-to-right/top-to-bottom traversal happens to match the intended narrative order 1→2→3), which is the right outcome — but it's incidental, not specified. A future implementation that reorders visually (CSS `order`, a differently-sequenced HStack, RTL handling, etc.) could silently detach visual order from AX/DOM order with nothing in the spec to catch the regression, which matters here specifically because one of the cards is often the equally-weighted hard-fail option.
  *Fix:* Add one sentence to EXPERIENCE.md's Accessibility Floor: "VoiceOver traversal order among choice cards follows their narrative/document order regardless of visual arrangement (vertical stack or horizontal row), so accessibility order and visual order never diverge."

- **low** — Rotate-mid-charge-cancels-hold `[ASSUMPTION]` isn't flagged as hold-path-only in the accessibility text.
  *Violates/risks:* Nothing FR-11-breaking — the tap-plus-undo-window path (the documented VoiceOver-compatible equivalent) is instant and unaffected by rotation, so no user is left without a non-gesture, rotation-safe path. But a motor-impaired user who specifically uses the hold path (rather than switching to tap) and inadvertently rotates the device while trying to hold steady for ~3s loses their in-progress charge — a plausible, avoidable frustration for exactly the population the hold-path's tap alternative exists to serve, and it's currently framed only as a general implementation note, not connected to accessibility impact.
  *Fix:* Add a one-line cross-reference in Accessibility Floor or the assumption itself: "this only affects the (already-optional) hold path — the tap-plus-undo-window path, and VoiceOver double-tap, are unaffected by rotation."

- **No issues found — contrast/color.** The only new visual elements in the landscape mockups ("margin" side labels, the tight-fit flag caption) are explicitly dev-reference/scaffolding annotations, not real app UI, and are correctly out of scope for AA. All real, app-facing content in the new mockups (choice-card ink-on-white text, eyebrow white-on-ink chip, button ink-on-cream/ink-on-transparent) reuses color tokens already audited in `review-accessibility.md`'s portrait pass — no new color pairing is introduced by the landscape treatment.

- **No issues found — `column-max-width-landscape` token value itself.** 680px is a reasonable measure for `{typography.body}` (20px/500 SF Pro) at roughly 60–70 characters per line, within the stated 60–75cpl target; not too wide or narrow as a design decision. (See the separate medium finding above for the mockups not actually implementing this value.) The cap's behavior at accessibility Dynamic Type sizes — fewer characters per line at the same 680px width as text grows — is expected/desirable and not a defect; no explicit exemption or override anywhere lets body text bypass the cap.
