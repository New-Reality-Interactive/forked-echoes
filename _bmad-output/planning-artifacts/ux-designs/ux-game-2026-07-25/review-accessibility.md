# Accessibility Review — Many-Worlds CYOA

Reviewed: DESIGN.md, EXPERIENCE.md, .memlog.md, all 5 mockups, PRD FR-11 (2026-07-25).

## Overall verdict

Not build-ready as-is. The spine gets the headline gesture story mostly right (hold-to-confirm with an explicit, repeated, three-times-stated tap equivalent, and a correct VoiceOver double-tap mapping), but it has one direct, provable contradiction of FR-11's hard constraint (page-turning has no documented non-gesture path at all), one clear WCAG AA contrast failure on a core recurring component in both color schemes, and an asymmetric-safety-net bug in the tap-commit path that specifically disadvantages the motor-impaired/VoiceOver users it claims to serve. These are fixable with spec edits, not a redesign, but they need another pass before an engineer should start building against this pair.

## Findings

- **critical** Swipe-driven page turn has no documented tap/VoiceOver-compatible equivalent (EXPERIENCE.md: Interaction Primitives — "Swipe left / right: page turn only"; Component Patterns — "Story page ... Swipe left advances, swipe right returns (FR-3)"). *Why it matters:* FR-11 is explicit and hard: "No interaction in the app is reachable *only* via a custom gesture." Page-turning is the single most frequent interaction in the entire app and, as documented, is reachable *only* by swipe. This is also a real iOS mechanics problem, not just a spec-wording gap: when VoiceOver is on, a one-finger swipe left/right is consumed by VoiceOver itself to move accessibility focus between elements — it is never delivered to the app as a page-turn gesture unless the app explicitly builds an alternate path (e.g., a "next/previous page" custom action, an edge-tap zone, or a visible button). Nowhere in DESIGN.md or EXPERIENCE.md is such a path specified. Every other gesture in the system (choice commit, run-options, interstitial Continue) got an explicit tap/VoiceOver equivalent in the Accessibility Floor section; page turn did not. *Fix:* Add an explicit tap-accessible page-turn affordance (e.g., tap zones on left/right thirds of the reading card, or a VoiceOver custom rotor action "Next page"/"Previous page" plus a small visible forward/back control), and state it in both the Component Patterns row for "Story page" and the Accessibility Floor section, mirroring how the choice-card tap equivalent is called out.

- **high** The tap-to-commit path — the one EXPERIENCE.md calls "the standard accessible tap equivalent" — is both instant and irrevocable, with no safety net, while the "primary" hold path has a built-in cancel (release before 3s to abort). *Why it matters:* Per FR-5 / Choice card behavioral rules, once committed a choice "locks... no re-selection control" is rendered at all. A user relying on tap (because they cannot sustain a 3-second hold — tremor, limited dexterity, or simply a VoiceOver double-tap) gets zero opportunity to reconsider or confirm before the choice is permanently locked, while a user using the primary hold gesture gets a natural "let go to cancel" grace period. A single mistouch, or a VoiceOver user who double-taps to explore rather than commit (a common VO interaction pattern), permanently locks an irreversible story choice with no undo and no confirmation step. The path meant to be *more* accessible is actually *less* forgiving than the primary path. *Fix:* Either (a) add a brief confirmation step or short undo window after a quick tap (e.g., "tap again to confirm" or a 1–2s undo toast) so the accessible path isn't strictly worse than the gestural one, or (b) if instant-commit-on-tap is a deliberate design choice, document the rationale explicitly and reconsider whether VoiceOver's double-tap-to-activate (which is unavoidable and not the user "choosing" instant commit the way a sighted tapper does) should route through the same instant-lock behavior.

- **high** `echo-callback.tag-color` (`{colors.accent-ember}`) as text on `{colors.surface-inverse}` background fails WCAG AA contrast in both color schemes (DESIGN.md tokens; confirmed in mockup CSS `.echo-tag{color:var(--frame-active)}` inside `.echo-line{background:var(--ink)}`). *Why it matters:* Computed contrast ratios (WCAG relative-luminance formula): light mode `#C2540F` on `#241C14` ≈ **3.65:1**; dark mode `#E0763A` on `#F3ECDD` ≈ **2.62:1** (worse, because dark mode's surface-inverse flips to a light cream while ember only brightens slightly). The "The story remembers" tag is 11–12px, weight 800–900, uppercase — well under the ~18.7px-bold / 24px-regular threshold for "large text," so it needs 4.5:1, not 3:1. This is the label for the app's signature callback moment, appearing 2–3 times every run, and it fails AA in both themes, more severely in dark mode. *Fix:* Either raise the tag's lightness/darken the ember value used specifically for this text role (a text-only "ember-on-ink" token distinct from the frame's decorative ember), or move the tag to `{colors.ink-on-inverse}` with ember reserved for a small icon/underline accent instead of the run of text itself.

- **medium** Trace-brass and ember are near-identical in luminance, making the frame's "powered up" state a pure hue shift with no lightness or shape cue behind it. *Why it matters:* Computed relative luminance: `trace-brass` `#8B6F47` ≈ 0.173, `accent-ember` `#C2540F` ≈ 0.178 — essentially indistinguishable by lightness alone. Orange vs. brown is a classic confusion pair for protanopia/deuteranopia (a meaningful share of male users). The functional information is *not* lost — the echo always co-fires with the echo-callback text block, and the Ending screen is disambiguated by completely different copy — but the app's own stated signature device ("Brand & Style": the frame "quietly suggesting a time-machine console... powers up to ember and glows") is silently non-functional as a standalone signal for CVD users; they only get the story's meaning via the accompanying text, never via the motif the design centers on. Dark-mode's brass/ember pair (`#C9A876` L≈0.418 vs `#E0763A` L≈0.291) has more separation, so this is worse in light mode specifically. *Fix:* Either accept this as a deliberate, purely-decorative-redundant signal (state it explicitly as a known/accepted limitation in DESIGN.md so it isn't mistaken for an oversight), or add a non-hue cue to the frame's active state itself (e.g., a distinct dash pattern, a filled vs. hollow via, or a brightness jump large enough to read on a luminance channel alone).

- **medium** Fixed-pixel circuit-corner geometry and absolutely-positioned interstitial art risk visual collisions at accessibility Dynamic Type sizes. *Why it matters:* The corner assembly is a hardcoded 30×30px box pinned to each frame corner (mockup: `.circuit-corner{width:30px;height:30px}` at `top:0;left:0`), while the reading card's top padding is a fixed 26px (`frame-well{padding:26px 18px 16px}`) — at default type size the eyebrow tag already sits only ~4px below the corner artwork. FR-11 requires body/echo text to "grow through accessibility sizes without truncation" via layout absorbing growth, but nothing scales the frame-well's fixed padding or the corner geometry alongside it, so an enlarged eyebrow tag or a wrapped first line of prose at AX accessibility sizes has a real, reasoned risk of running behind/into the corner trace. Separately, the branch-arrival interstitial's headline (`.headline{position:absolute;top:56%;left:20px;right:20px}`, 34px/900/uppercase, unclamped per typography tokens) is layered over fixed-position decorative CSS art (a circle positioned at `top:26%;left:60%;width:160px`) with no reflow relationship between the two — growing that headline 2–3x at accessibility Dynamic Type sizes is likely to overlap the art rather than push it aside, since the art's position is independent of text metrics. *Fix:* Specify that frame-well padding and corner-assembly clearance scale (or at minimum have generous fixed headroom reserved) relative to the largest supported Dynamic Type category, and specify how/whether the interstitial's art repositions or fades when its headline wraps to 2+ lines at accessibility sizes.

- **medium** No mapping from design typography roles to iOS Dynamic Type text styles. *Why it matters:* DESIGN.md gives literal pixel values ("34px", "20px", "17px", "12px") per role and says each "must scale with system setting," but never states which `UIFontTextStyle` (`.largeTitle`, `.body`, `.caption1`, etc.) or scaling curve each role should bind to. Without that contract, two engineers (or the same engineer under time pressure) could implement "scaling" as a manual multiplier keyed off the system's content-size category rather than semantic text styles, producing roles that scale at different, inconsistent rates relative to each other — quietly breaking the "confidence comes from scale and weight contrast" relationship DESIGN.md's Typography section says is load-bearing. *Fix:* Add an explicit token-to-text-style mapping table (e.g., headline → `.title1`/custom scaled metrics, body/echo-callback → `.body`, choice-label → `.headline`, eyebrow/meta → `.caption2`) so scaling behavior is implementable and testable, not just directionally intended.

- **medium** Reduce Motion guidance enumerates only two animated moments and leaves the page-turn transition and interstitial entrance/exit unaddressed. *Why it matters:* EXPERIENCE.md's Reduce Motion bullet covers exactly two things: the choice-card charge-fill and the frame's echo glow. But DESIGN.md's Brand & Style section separately asserts "That is the only thing in this system allowed to animate/glow; everywhere else stays still and confident" — a blanket claim that implies the swipe-driven page turn and the full-bleed branch-arrival interstitial's appearance/dismissal have *zero* visual transition at all. That's plausible but is never stated as a deliberate decision, and it's in tension with normal paged-reader UX expectations (a swipe gesture with literally no visual response, not even a cross-fade, commonly reads as broken/unresponsive touch handling). If an engineer instead implements a natural page-curl/slide transition (very likely, since the surface is explicitly modeled as "paged"), that's an animated moment with no Reduce Motion treatment specified anywhere. *Fix:* Explicitly state, in the Reduce Motion section (not just inferred from a brand-tone paragraph elsewhere), whether page turns and the interstitial transition are animated at all under normal conditions, and if so, what they collapse to under Reduce Motion.

- **low** Run-options button (`ellipsis.circle` SF Symbol) has no specified `accessibilityLabel`. *Why it matters:* The Accessibility Floor section details VoiceOver labels/states for choice cards but says nothing about this control's spoken name; a default SF Symbol VoiceOver name may not clearly convey "opens exit/restart options" to a blind user. *Fix:* Add "Run options" (or similar) as the explicit accessibilityLabel in the Accessibility Floor section, matching the treatment already given to choice cards.

- **low** `ink-secondary` on `surface-base` in light mode passes AA only marginally (~4.85:1 against the 4.5:1 minimum for normal-weight text), used for pager/meta/caption roles that are small and uppercase-tracked. *Why it matters:* This is close enough to the AA line that font-rendering/anti-aliasing differences or a slightly different final hex during implementation could tip it under 4.5:1; it's used for wayfinding chrome (page number, chapter meta) that some users specifically need to read to track progress. *Fix:* Either darken `ink-secondary` slightly for a larger safety margin, or confirm this pairing is only ever used at caption-level (17px) rather than the smaller 12px meta/pager role and document that constraint.

- **low** No mention of iOS "Bold Text" or "Increase Contrast" accessibility settings interacting with the system's deliberately weight-driven hierarchy (headline 900 vs. body 500 vs. choice-label 800). *Why it matters:* DESIGN.md states the confidence/hierarchy in this UI comes specifically from weight contrast between roles, not size or color. If "Bold Text" is on, iOS can push already-heavy weights (800/900) further and change how distinctly body (500) reads against them, potentially flattening the intended weight relationship system-wide. Not a blocking issue, but worth a stated position. *Fix:* Note in DESIGN.md whether the type system is expected to remain legible/intentional under Bold Text, or accept it as an unhandled edge case.
